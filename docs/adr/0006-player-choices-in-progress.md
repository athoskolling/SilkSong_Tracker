# Progress also keeps a few player choices: opened Crest slots and saved Builds

Decided with Athos, 2026-10-20 (Phase 5, second round of answers). Adds to ADR 0001; does not reverse ADR 0005 for Rosaries.

**Change, 2026-10-20 (third round, ADR 0007): `shellShards` is dropped.** This ADR first proposed a third field, a Shell Shards number the player types, as the orchestrator's provisional reading of Athos's answer. Athos chose the other reading: Shell Shards work like the Rosaries, worked out from entries. So there is no `shellShards` field, no `setShellShards`, and no Firestore rules change (the rules never accepted the key, and still refuse it). The code never built the field. The text below keeps the two fields that were built; where it once named `shellShards`, that part no longer applies.

Until Phase 5, Progress held only ids (`done`, `visited`), so union merge covered everything. The Build picker needs two things that are not "an entry is done": how many slots the player opened on each Crest with Memory Lockets (a choice made at a bench, not a thing obtained), and the Build they saved for each Crest. Progress gets two optional fields for them: `crestSlots` (Crest id to `{ colour: number }`) and `builds` (Crest id to `{ colour: [entry ids] }`). The shapes are in `docs/CONTRACTS.md` sections 1 and 3.

**How they merge.** After the first sign-in on a device nothing changes: the copy with the larger `updatedAt` wins as a whole object, these fields included. On the first sign-in, where ADR 0001 takes the union of ids, each field has its own "union": opened slots take the larger number per Crest and colour (Memory Lockets are spent and never given back, so a larger number is something the other copy did not record); Builds keep every Crest saved on either side, and where both sides saved one for the same Crest, the one from the newer copy is kept whole (two half-Builds glued together could hold more Tools than the Crest has slots). A backup import follows the same idea but never replaces anything already there: opened slots take the larger number, and a Build is added only for a Crest with none saved.

**Older versions of the site.** A device that still runs a page from before this change writes Progress without these fields. With plain "newer wins", its next tick would erase every saved Build on every device. So a field that is missing from a copy means "this copy was written by a version that does not know the field", not "empty", and the merge takes that field from the other copy. The new code never drops a field it has once written; "Start a new run" writes them as empty on purpose, so an empty value still wins as newer.

**Rejected alternatives.**
- *Encode the choices as ids in `done`* (for example `reaper-crest:blue:1`), so union merge needs no change. Rejected: `done` holds entry ids only (contract section 1); fake ids would enter counts, the Route and every requirement function, and a typo could never be caught by the validator.
- *Do not store them; work them out from `done`.* Rejected for opened slots, because where a Memory Locket was spent is the player's choice and no entry records it; and for Builds, because Athos asked for saving one.
- *A separate Firestore document or localStorage key for them.* Rejected: two documents can be half written, and every merge, import, export and "Start a new run" path would have to handle both. One object keeps one `updatedAt` and one rule.
- *Bump the localStorage key to `:v2`.* Rejected: everyone's saved Progress would look empty. The fields are optional, so `:v1` stays.
- *A typed Shell Shards number* (third field, `shellShards`). Proposed here first, dropped by Athos on 2026-10-20 (ADR 0007): it would go stale as soon as the player spends in the game, which is why ADR 0005 kept Rosaries out of Progress.

**Costs.** The Firestore rules have to accept the two optional keys, and Athos has to publish them **before** the new `progress.js` reaches the published site; until then any write that carries them would be refused (local data stays safe, the sync line shows an error). A device that still runs an older page keeps its own copy without the fields and drops them from the cloud document on its next change; any device running the new page writes them back on its own next change.
